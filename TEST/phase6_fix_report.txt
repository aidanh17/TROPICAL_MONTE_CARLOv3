(A) REAL BUG #34 — computeFanScaled $Failed on lifted COMPLEX 8D vertices
=======================================================================
ROOT CAUSE (found by reproduction, scratchpad/probe34.wl):
  LiftCoefficients[spec, liftRules] read the aux-variable power as r["k"].
  But DetectExtremeCoefficients ships its rules with key "SuggestedK", and
  EvaluateTropicalMCLifted only remaps SuggestedK->k internally — when a
  detector rule is passed straight to LiftCoefficients (as cc_34 and the
  general public API do), r["k"] resolved to Missing[KeyAbsent, k].
  This poisoned the lifted monomial:
     ((1/1000000 + I/1000000) x[1]^2 x[9]^Missing[KeyAbsent,k]) / z0^Missing...
  so the lifted Newton-polytope vertex became
     {2,0,0,0,0,0,0,0, Missing[KeyAbsent,k]}
  and ComputeDecomposition/computeFanScaled wrote "$Failed" into the
  Polymake INEQUALITIES input -> $Failed.

FIX (tropical_eval.wl, LiftCoefficients, ~line 835):
  - Added a local resolver  ruleK[r] := Lookup[r,"k", Lookup[r,"SuggestedK", Missing["NoK"]]]
    used at all three k-reads (primary z0 exponent, residual c_i = C_i/z0^k_i,
    and the lifted-monomial aux power auxVar^k_i).
  - Added an up-front guard: every rule must resolve to a positive INTEGER
    aux power (the lift identity needs an integer); otherwise fire
    TropicalEval::liftbadvar and return $Failed cleanly (no Missing[] leaks
    into a vertex).
  - liftData["Rules"] still stores the original liftRules unchanged, so any
    downstream reader of LiftData is unaffected.

(E) REAL ENGINE BUG #27 (§5.8) — the badcpp guard was INEFFECTIVE  [THIS RUN]
=======================================================================
ROOT CAUSE (confirmed by probe, scratchpad/probe_cform.wl):
  cppBadTokens (tropical_eval.wl, was ~line 3235) scanned the generated C++
  for BRACKET-form head tokens:
     {"DirectedInfinity","ComplexInfinity","Indeterminate",
      "Sin[","Cos[","Sqrt[","Plus[","Times[","Power[","Rule[","List["}
  But codegen emits unconverted heads via CForm — mmaToCInternal's terminal
  fallback is  ToString[CForm[expr]] — and CForm formats a head in PAREN form,
  never bracket form:
     CForm[Sin[x[1]]]    -> "Sin(x(1))"
     CForm[BesselJ[0,x]] -> "BesselJ(0,x(1))"
     CForm[Power[a,b]]   -> "Power(a,b)"
  So NONE of the "Sin[" / "Cos[" / ... bracket tokens ever matched the actual
  output.  The badcpp scan silently returned {} on broken code, and
  GenerateCppMonteCarlo / GenerateCppMonteCarloIBP Exported uncompilable C++
  (an unsupported head) instead of returning $Failed.  (Two further latent
  defects: "ComplexInfinity" as a literal NEVER appears either — CForm renders
  ComplexInfinity AS "DirectedInfinity()"; and "Plus["/"Times[" were dead
  since MmaToC has explicit infix DownValues for Plus/Times that never reach
  the fallback.)

FIX (tropical_eval.wl, cppBadTokens + new cppBadHeads, ~line 3231):
  - Symbolic infinities/indeterminate: scan literal substrings
    "DirectedInfinity" (also covers ComplexInfinity, which prints thus) and
    "Indeterminate".
  - Unconverted heads: match the ACTUALLY-EMITTED PAREN form  Head(  with a
    leading word boundary  (?<![A-Za-z0-9_])  and the "(" regex-escaped, over
    an EXPLICIT deny-list cppBadHeads (74 heads: trig/hyperbolic + inverses,
    Sqrt/Power/Surd, Gamma/PolyGamma/Beta, Zeta/PolyLog/Lerch, Bessel/Airy,
    Erf/Erfc/Erfi/Fresnel, elliptic, hypergeometric/MeijerG, exp/log integrals,
    Sign/Floor/Ceiling/Mod/Max/Min/Piecewise, and the structural Rule/List/
    Rational/Complex).
  - DELIBERATELY EXPLICIT (not a blanket "any Uppercase(" scan): a blanket
    scan false-positives on the GENERATED C++ identifiers the goldens contain —
    P0(, Pfull0(, Psimp0( (polynomial evaluators) and the CUBA Vegas( entry
    point (verified: a blanket [A-Z][A-Za-z0-9]*\( regex matches exactly those
    four in the 9 goldens).  Supported heads are always emitted lowercase/
    std::-qualified (std::sin, std::sqrt, std::pow, std::log, std::exp,
    std::abs), so a capitalized "Head(" from the deny-list can only be CForm
    leakage — the guard fires there and nowhere else.
  - Both codegen entry points (GenerateCppMonteCarlo @ ~3303,
    GenerateCppMonteCarloIBP @ ~5064) call the same cppBadTokens, so one edit
    fixes both paths.

ALSO (test consistency): TEST/cc_27.wl (D) belt-and-suspenders token check
  updated from bracket form "Sin[" to the emitted paren form "Sin(" (and
  dropped the never-emitted "ComplexInfinity" literal in favor of
  "DirectedInfinity").  The primary (D) assertion (rCpp === $Failed) was
  already correct; this only aligns the secondary file-content check.
